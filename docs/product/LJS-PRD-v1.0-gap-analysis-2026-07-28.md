## 1. 审查结论

当前 LJS 已经具备“招聘数据采集引擎”的主要工程骨架，但尚未形成 PRD 定义的“招聘机会管理产品闭环”。

已完成度最高的是：

- 公司、招聘入口、招聘事件和岗位的基础领域模型；
- 确定性官网与 ATS 验证；
- 搜索候选与正式数据分离；
- SQLite 幂等写入、批次断点和失败隔离；
- 本地优先、浏览器兜底的采集链；
- 基础质量报告与学生 XLSX 导出；
- Worker、Profile 锁、熔断器和本地控制面。

主要缺口是：

- 已验证招聘入口没有稳定转化为招聘事件和可投递岗位；
- 缺少固定公司池的周期调度、增量差异和岗位上下线闭环；
- 缺少结构化审核任务、岗位质量等级和发布门禁；
- 缺少岗位分配、保存、投递、忽略、错误反馈等用户行为模型；
- 缺少基于用户行为的公司优先级、岗位排序和复检频率反馈；
- 缺少正式的质量与运营看板；
- 当前学生导出仍可能包含 `PLATFORM_ONLY` 数据，不符合“学生端原则上只展示 A 级岗位”的 PRD 原则。

因此，当前状态更接近 PRD 版本规划的“阶段 1 工程基础已具备，但真实闭环尚未验收”，还不能认定阶段 1 完成。

## 4. 数据模型差距

### Company

已有：标准名称、中英文名、别名、官方域名、行业、国家地区、市场。

缺少或不完整：

- 母公司、子公司和品牌关系；
- 招聘域名与主业务域名的明确区分；
- 公司监控状态；
- 数据来源和最后人工审核时间；
- 负责人。

### CareerPortal

已有：URL、ATS 类型、页面类型、验证状态、置信度、来源等级、招聘可用性和最后检查时间。

缺少或不完整：

- ATS 企业/租户标识的正式字段；
- 是否需要浏览器；
- 固定抓取方式和访问频率；
- 最近成功与最近失败时间；
- 监控状态和负责人；
- 审核历史。

### JobOpening

已有：原始/标准岗位名、岗位族、地区、类型、发布日期、截止日期、详情页、申请入口、状态和首次/最后发现时间。

缺少或不完整：

- 工作模式与经验要求；
- 独立招聘类型字段或稳定事件映射；
- 质量等级 A/B/C；
- 明确的去重指纹字段；
- 申请入口最后有效性检查时间；
- 自动发布/审核/拒绝的发布状态。

### SourceEvidence

当前 `verification_evidence` 能保存证据代码、方向、权重、观察值、来源 URL 和时间，但尚未完整覆盖：

- 页面标题与域名快照；
- HTTP 状态与重定向链；
- 页面摘要或内容快照引用；
- ATS 指纹快照；
- 判定结果、判定依据和证据版本。

### MonitorTask

当前 `control_tasks` 仅覆盖岗位词、地区、行业、时间、数量、选择模式和百度兜底，尚未覆盖：

- 创建者、公司范围和排除条件；
- 经验要求与招聘类型；
- 更新频率、接收人和最近运行时间；
- 调度状态与下一次运行时间；
- 市场覆盖计划。

### ReviewTask

缺失。当前仅有入口 `REVIEW` 状态，没有结构化审核任务、审核人、结果、字段修改和历史记录。

### UserAction

缺失。当前没有岗位保存、忽略、分配、已投递、错误反馈或重新验证触发记录。

## 5. 关键产品偏差

### 5.1 学生输出门禁不符合 PRD

PRD 要求学生端原则上只展示 A 级岗位。当前没有质量等级模型，学生 XLSX 会纳入未被官方入口替代的 `PLATFORM_ONLY` 招聘事件。现有 8 条投递表记录中，6 条来自第三方平台，不能作为 A 级官方岗位发布。

### 5.2 “任务成功”仍不等于“有效岗位”

当前大量批次结果是 `PARTIAL`，能够完成页面检查或入口验证，但没有形成招聘事件和岗位。控制面需要同时展示：

- 公司处理完成；
- 官方入口验证完成；
- 当前招聘状态确认；
- 岗位抽取完成；
- 投递入口验证完成；
- 正式发布完成。

### 5.3 搜索发现与日常监控仍需彻底分离

搜索引擎应只用于新公司、新入口和失效入口的低频发现。已确认入口的日常岗位监控必须由 ATS Adapter、JSON、HTTP 或静态 HTML 路径完成；浏览器只用于动态页面兜底。

### 5.4 缺少用户结果数据

目前无法计算 PRD 的北极星指标“每周有效行动岗位数”，因为系统没有记录保存、分配、投递等用户行为。

## 6. 推荐后续开发路线

### Step 0：稳定当前工程基线

目标：把当前大量未提交实现整理为可回滚、可发布的版本。

1. 盘点并拆分当前 dirty worktree；
2. 将核心实现、迁移、测试、文档按范围形成独立提交；
3. 运行完整测试、迁移升级测试和 SQLite 备份恢复测试；
4. 固化 V1.0 PRD、架构决策和变更确认机制；
5. 冻结首个 MVP 公司池、岗位方向和验收样本。

完成标准：可从干净分支重建数据库并复现测试结果。

### Step 1：补齐阶段 1 的增量监控闭环

目标：不再依赖“重新搜索所有公司”，而是稳定检查已确认入口。

1. 建立 MonitorTask 与调度计划；
2. 将固定公司池拆成 ATS/JSON、HTTP、静态 HTML、浏览器兜底四类；
3. 建立岗位快照和新增、更新、下线差异；
4. 增加申请入口有效性检查；
5. 标准化失败分类、重试和冻结策略；
6. 优先补齐覆盖数量最高的 ATS/动态招聘站 Adapter；
7. 对 50–100 家固定公司池连续运行 7 天。

完成标准：连续运行可稳定产生官方新增岗位，而不是只验证入口。

### Step 2：建立正式岗位发布门禁

目标：只有来源、入口和关键字段达到标准的岗位进入正式库。

1. 增加岗位质量等级 A/B/C；
2. 增加发布状态：候选、待验证、待提取、待入口验证、待审核、已发布、已拒绝、已失效；
3. 学生端只展示 A 级；
4. 规划师端默认展示 A/B 级；
5. `PLATFORM_ONLY` 只进入候选或审核，不进入学生正式投递表；
6. 建立质量评分、证据版本和申请入口最后验证时间。

完成标准：学生输出不再混入第三方候选或无法确认申请入口的数据。

### Step 3：补齐审核与内部交付闭环

目标：让运营人员能处理不确定数据，并让职业规划师使用岗位。

1. 新增 ReviewTask、ReviewDecision 和结构化字段修正；
2. 新增岗位分配；
3. 新增 UserAction：保存、忽略、已投递、失效/错误反馈；
4. 建立审计日志和角色边界；
5. 提供最小内部岗位列表、审核队列和任务状态页面。

完成标准：一条岗位可以从候选进入审核、发布、分配和反馈。

### Step 4：质量看板与反馈策略

目标：用产品结果而不是抓取数量驱动优化。

1. 计算官方来源率、申请入口有效率、字段完整率、重复率和失效率；
2. 统计浏览器兜底率、人工审核率、连续运行成功率和失败分布；
3. 统计保存率、分配率、投递率和错误反馈率；
4. 计算每周有效行动岗位数；
5. 根据用户行为调整公司优先级和复检频率。

完成标准：能够解释本周系统产生了多少可被真实使用的岗位，以及损失发生在哪一层。

### Step 5：扩大新公司发现

目标：在固定公司池闭环稳定后，再扩大市场覆盖。

1. 定期生成候选公司；
2. 搜索和公开来源只产生候选；
3. 确定性验证与审核后进入正式公司池；
4. 建立候选来源质量和新增公司转化率；
5. 根据行业与岗位方向补充公司池。

完成标准：新公司不会绕过官网/ATS 验证和发布门禁。

### Step 6：学生端与个性化

在内部闭环、质量门禁和用户行为稳定后，再开发学生岗位中心、提醒、偏好学习和简历匹配。

## 7. 下一迭代建议

下一迭代应只做两件事：

1. 清理并发布当前工程基线；
2. 实现“固定公司池增量监控 + 正式岗位质量门禁”的最小闭环。

暂不继续扩大公司数量，不优先开发完整前端，也不把浏览器搜索作为主要数据生产方式。

建议首个验收样本：

- 中国市场；
- 50 家已确认招聘入口的公司；
- 校招全职、校招实习、日常实习；
- 连续运行 7 天；
- 学生输出只包含 A 级官方站或可信 ATS 岗位。
